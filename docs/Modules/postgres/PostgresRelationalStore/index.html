PostgresRelationalStore

Webda/PostgresRelationalStore stores models in typed tables: one column per field, primary and foreign keys, junction tables for the link collections, indexes. The schema is generated from the compiled model metadata by @webda/sql-schema; the models, the Repository<T> API, WebdaQL and the repository events are the same as with the JSONB PostgresStore.

{
  "services": {
    "Registry": { "type": "Webda/PostgresStore", "postgresqlServer": { "host": "localhost", "database": "webda" } },
    "domain": {
      "type": "Webda/PostgresRelationalStore",
      "models": ["MyApp/User", "MyApp/Post", "MyApp/Comment", "MyApp/Tag"],
      "postgresqlServer": { "host": "localhost", "database": "webda" },
      "usePool": true,
      "schemaSync": "alter"
    }
  }
}

JSONB or relational?​

Schema changesnone neededadditive, at init() or by hand
Unknown propertieskept in datakept in the _extra JSONB column

Link collectionsan array inside dataa junction table

Keep the JSONB store as Registry (it accepts every model, configuration and internal state) and use the relational store for the domain models whose shape is stable. Both can share one postgresqlServer (pools are shared by configuration).

Every column is created nullable (the model schema validates required); foreign keys are DEFERRABLE INITIALLY DEFERRED, so self references and cycles insert in one transaction.

class User extends UuidModel {
  /** @Unique */
  email: string;
  /** @Index byNameDay */
  name: string;
  /** @Index byNameDay */
  day: string;
}

DATE columns and time zones. A DATE column holds a calendar day, never an instant: the store writes the first ten characters of the value, i.e. the written day of a YYYY-MM-DD or ISO date-time string (whatever its offset) and the UTC day of a Date object (new Date("2024-03-04T23:30:00-05:00") is stored as 2024-03-05). It reads back as the YYYY-MM-DD text, whatever the time zone of the server or the process, and compares as that text (day >= '2024-02-01'). A TIMESTAMPTZ column holds an instant and reads back as its ISO 8601 UTC text.

Schema lifecycle​

At init() the store builds the plan, takes an advisory lock (pg_advisory_xact_lock on the store name) in a transaction, describes the database under it, reads the live application versions from the registry (see below), refuses an incompatible plan, applies schemaSync, records its own version and commits. It is never destructive: no DROP, no type change, no SET NOT NULL, no rename. What alter cannot resolve (a column of another type, a column no version knows) is logged at WARN; validate throws SchemaDriftError (SCHEMA_DRIFT) for the same differences and for anything missing. The columns of the other live versions are never drift.

On a table that already has rows and traffic, alter keeps the heavy work out of the DDL transaction: an index is built CONCURRENTLY after it (a failed build, duplicates under a new unique index for example, is logged and the index dropped), a foreign key is added NOT VALID in the transaction and validated after it, so no ACCESS EXCLUSIVE lock outlives the catalog update.

webda postgres schema show           # one line per table with its columns
webda postgres schema show --sql     # the CREATE statements of the whole plan
webda postgres schema show --diff    # connect, print what `alter` would run, then `-- ` lines for the drift (exit 1)
webda postgres schema show --json    # the plan
webda postgres schema check          # compare the plan with the live versions (exit 1 on a BLOCK)
webda postgres schema contract --dry-run
webda postgres schema retire --version 1.4.0
webda postgres schema backfill --table post --from title --to headline

Teams with their own migration pipeline run schemaSync: "none" or "validate" and apply --sql / --diff with their tooling; the registry and schema check still protect them.

Several app versions on the same database​

Blue/green, canary and rolling deployments run several versions of the application at the same time against the same tables. The store makes that safe with the expand/contract pattern: the physical schema is the union of every live version, each version only reads and writes its own projection.

  • Every statement names its columns from the plan of its version (never SELECT *), update() only replaces the columns of its own projection, _extra is merged (_extra || $n) so the keys of another version survive, unknown columns are ignored on read and a __type only the newer version knows is skipped by the class filter.
  • A new required field is created nullable: NOT NULL waits for the contract phase, the application validates until then.
  • Registry. Each running version is a Webda/SchemaVersion entry (uuid = <store>:<appVersion>:<planHash>, the full plan, status LIVE | RETIRED, firstSeen, lastHeartbeat, the instances map, forced). Nobody claims the model, so it lands in the Registry catch-all (JSONB, memory, Mongo...), never in a relational table. Each instance heartbeats with a partial patch() every versionHeartbeat seconds; a version silent for longer than versionTtl no longer counts. The flow at init() is lock → read live versions → check → DDL → upsert own version → unlock. If the registry cannot be read or written, init() fails closed (SCHEMA_REGISTRY_UNAVAILABLE, fatal, no DDL). A MemoryStore registry only knows the versions of its own process: a WARN says the checks are limited to the process.
  • Compatibility check, on every startup whatever schemaSync: the plan is compared field by field with the plan of every live version by compareSchemaPlans (@webda/sql-schema, a pure function). Additions, widenings, a field becoming required or removed are SAFE; added enum values, a rename (remove + add) and a new unique index are WARN; a property type change, a narrowing, removed enum values, a field becoming optional while the live version requires it, a relation kind or target change, a delete policy change, a primary key, hierarchy or layout option change are BLOCK. A BLOCK refuses to start with SchemaIncompatibleError (HTTP 409, SCHEMA_INCOMPATIBLE_ERROR, wrapped in a FatalInitError) naming the table or column, the live version and the expand/contract recipe; the database is untouched and the refused version is not registered. allowIncompatible (or schema check --force-incompatible) downgrades a change you accept to a forced WARN, recorded in the version.
  • webda postgres schema check [--against <version>] [--json] prints the same table for CI (exit 1 on a BLOCK, 2 when --against matches nothing), so a pull request changing a property type fails before the deploy, not at the canary's startup. Run it against the production registry, read-only.
  • Contract phase, never run by init(): webda postgres schema contract [--dry-run] computes the union of the versions still live and proposes what is now safe: drop the columns and tables no live version uses (only what a retired or expired version planned: a DBA's column is left alone), SET NOT NULL where every live version requires the field (skipped when a row is null), validate the foreign keys still NOT VALID. webda postgres schema retire --version <id | appVersion | planHash> retires a version first.
  • Renames and type changes are expand / backfill / contract: add the new field (headline, statusCode), webda postgres schema backfill --table post --from title --to headline [--batch 1000] copies the column by batches where the target is null, switch the reads, retire the old version, contract.

Per-version views, schemaPerVersion and the dual-write trigger of the design are not implemented.

Reads and writes​

  • Every statement names its columns from the plan: a row written by an older application version keeps the columns this version does not know, update() only replaces the columns of its own projection and merges _extra.
  • Junction rows are written in the same transaction as the owner row and read with one statement per junction per page. With usePool each transaction takes its own connection; on a single client every statement of the store goes through one lock, so a plain write never runs inside another caller's transaction.
  • With "transaction": "operation" (see PostgresStore), every statement of an operation runs in the operation transaction: the owner row and its junctions join it instead of opening their own.
  • WebdaQL: =, !=, <, <=, >, >=, LIKE, IN, IS NULL, IS NOT NULL, ORDER BY, LIMIT/OFFSET on columns and JSONB paths, CONTAINS on JSONB arrays, with the in-memory semantics (views = '1' matches a BIGINT, views = 'abc' matches nothing, != matches NULL). A time column compares natively with a date or a date text and reads as its ISO text otherwise: _lastUpdate = 'abc' matches nothing, _lastUpdate LIKE '2024-05%' and day LIKE '2024-05%' match the ISO form the models store. NULL sorts first ascending, last descending.
  • WebdaQL on link collections, as an EXISTS sub-query on the junction: tags CONTAINS 't1' (the collection links to the key; a composite key is split), contributors.role = 'editor' (one item matches: a target key part such as contributors.uuid, a typed link field or a path in the attributes column), on a map the second segment is the item key (reviewers.lead.since > 2020, reviewers.lead IS NULL). A link collection reads as an array or a map, never null: tags IS NULL is FALSE. These comparisons work in every statement (query, count, updateMany, deleteMany, aggregations); the in-memory stores do not match item attributes this way.
  • WebdaQL on a reference to a composite key compares its key parts: pair = 'x_y', pair != 'x_y' and IN split the value on the key separator (a value that does not split matches nothing, everything for !=), LIKE and the ordering operators compare the joined text, IS NULL holds when every part is NULL.
  • incrementAttributes works on numeric columns; upsertItemToCollection / deleteItemFromCollection work on JSONB arrays and on simple link arrays (by position); updateMany assigns columns and JSONB paths (one assignment per JSONB column); deleteMany is one DELETE.
  • Aggregations and count run in SQL (native: true).

Mapped attributes​

A ModelsMapped<Post, "author", "title"> is a denormalized copy kept by a ModelMapper on the document stores. When the mapped model (Post) is listed in the same relational store and its link (author, a reference or a link collection) targets this model, the store fills the attribute on read instead: one statement per attribute and per page of rows selects the rows of the mapped model (and of its subclasses) linking to each owner, in primary key order, and each item holds the mapped attributes and the uuid of the row (a composite key is joined). The attribute is never written (a value given on create / patch is ignored) and cannot be filtered: query the mapped model instead. Do not attach a ModelMapper to these models. A link collection of the mapped model is not copied into the items. A ModelsMapped whose model is served by another store keeps the previous behaviour (stored in _extra).

Promoting a model from the JSONB store​

A model served by the Registry (or any PostgresStore) moves to the relational store in three steps: list it in models, start the application (schemaSync creates its typed table), then import its rows:

webda postgres import --models MyApp/Post,MyApp/Tag --source Registry --purge

importFromJsonb(source, { models, purge }) reads the rows through the JSONB repository of the source and writes them through the relational repositories in one transaction: the links between the imported rows can point in any direction (deferred foreign keys), a row whose key is already in the relational table is skipped, and a failure (an unknown link target, a duplicate) rolls everything back. With purge, the rows are deleted from the source once committed. The JSONB table and the relational table of a model must have different names: name one of them with tables (the default name is the same on both stores). On a single client the import runs on its own transaction; with usePool it joins withTransaction().

Limitations​

  • No ORDER BY on a junction attribute or on a reference to a composite key.
  • A ModelsMapped is only filled when its model is in the same store.
  • No MigratableStore raw access (there are no Webda 3 JSON rows in a typed table).
  • A JSON null stored in a JSONB column reads as an absent field.

Follow-ups tracked in #838: per-version views and schemaPerVersion (#1016).

Other engines​

The same layer renders on SQLite with SQLiteRelationalStore. MySQL / MariaDB (#1010) and SQL Server (#1011) are not implemented: each is one RelationalDialect and one store. Please upvote and comment on those issues if you need them.
