# Webda configuration

## When to use

Enabling or configuring a service, or setting application parameters.

## Pattern

`webda.config.json` declares the services and their parameters. `npm run build` generates `.webda/config.schema.json`, referenced by `$schema`, so editors validate the file.

```json
{
  "$schema": ".webda/config.schema.json",
  "version": 4,
  "parameters": {
    "supportEmail": "support@example.com"
  },
  "services": {
    "HttpServer": { "type": "Webda/HttpServer" },
    "ReminderService": { "type": "ReminderService", "delayHours": 12 }
  }
}
```

- `type` is `Namespace/Name`; types of your app can omit the namespace.
- `parameters` are shared by every service; a few keys are framework settings (`website`, `apiUrl`, `metrics`), any other key is yours.
- Values are not interpolated: `${VAR}` stays a literal string. Secrets come from the environment variables each service reads (for example `WEBDA_MONGO_URL`, `PGHOST`), never from the file.

Read the configuration in code through the service parameters (`this.parameters.delayHours`) or the application parameters:

```ts
import { useParameters } from "@webda/core";

export function supportEmail(): string {
  return useParameters().supportEmail;
}
```

## Common mistakes

```text
"mongoUrl": "${MONGO_URL}"             → not interpolated; use the service's environment variable
Secrets committed in webda.config.json  → environment variables, documented in .env.example
Editing .webda/config.schema.json       → generated by npm run build
```

## Verify

`npm run build` (schema), then `npm run debug`: an invalid service configuration fails at startup with the service name.
