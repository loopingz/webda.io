Knative and Cloud Run

Webda/KnativeDeployer (@webda/kubernetes) deploys the application as a Knative Serving Service: a container serving HTTP, scaled on demand (down to zero), with revisions and traffic splitting. Google Cloud Run implements the same API, so the same manifest works there with platform: "cloudrun".

The deployer only needs a cluster with Knative Serving installed (and an ingress like Kourier or Istio), or a Cloud Run project: installing them is out of scope.

Setup​

Declare the deployer as a unit of a deployment, usually after the Webda/ContainerDeployer building the image:

deployments/production.jsonc
{
  "units": [
    {
      "name": "image",
      "type": "Webda/ContainerDeployer",
      "image": "ghcr.io/acme/api",
      "tags": ["${git.version}"]
    },
    {
      "name": "knative",
      "type": "Webda/KnativeDeployer",
      "containerDeployer": "image",
      "namespace": "apps",
      "minScale": 1,
      "maxScale": 20,
      "containerConcurrency": 80,
      "env": { "NODE_ENV": "production" },
      "envFrom": [{ "secretRef": { "name": "api-secrets" } }],
      "traffic": [
        { "latestRevision": true, "percent": 90 },
        { "revisionName": "api-4f2a1c3", "percent": 10, "tag": "previous" }
      ]
    }
  ]
}
webda -d production knative manifest   # prints the Service, touches nothing
webda -d production deploy             # pushes the image, applies the Service, waits for Ready
webda -d production knative status     # URL, revisions and traffic
webda -d production knative delete --yes

deploy runs the deploy command of every unit of the deployment: with containerDeployer set, the Knative unit calls the image unit itself and pins the revision to the pushed digest (ghcr.io/acme/api@sha256:...), so leave the ContainerDeployer unit first or let the Knative unit push for it. Without containerDeployer, set image to the reference to deploy (templates like ${git.version} apply).

The Service is created, then server-side applied with the webda field manager: fields set by other tools (a kubectl annotate) are kept, the fields of the manifest are owned by webda. deploy then waits for the Ready condition of the new generation (readyTimeout, 300s) and prints the URL; a Ready=False condition fails the command with its reason and message (KNATIVE_NOT_READY).

Runtime: what the application does for Knative​

Nothing specific is needed in the application:

  • Port: Knative and Cloud Run inject the PORT environment variable; the HttpServer listens on it when its port parameter is not set (the configuration always wins over the environment).
  • Readiness: the deployer sets WEBDA_HEALTH_PATH in the container to healthPath (/healthz), which enables the probe route of the HttpServer. It answers 200 {"status":"ok"} once Core finished init(), 503 {"status":"starting"} before, and 503 {"status":"stopping"} while the server drains. The route is answered before the routing and needs no authentication. Set healthPath to "" for a TCP probe instead.
  • Graceful shutdown: on SIGTERM, the CLI stops the HttpServer: it refuses new connections, answers 503 on the health path and waits for the requests in the web pipeline up to shutdownGracePeriod (10s), then closes every connection (idle keep-alive, streams kept open after their handler, gRPC streams) and stops the services. Keep shutdownGracePeriod below the revision timeoutSeconds (Knative uses it as the pod termination grace period) and expect requests longer than the grace period to be cut.
webda.config.json (optional, the environment enables the same)
{
  "services": {
    "HttpServer": { "healthPath": "/healthz", "shutdownGracePeriod": 10000 }
  }
}

Revisions​

With the default revisionSuffix, the revision is named after the commit (api-4f2a1c3): deploying the same commit twice applies the same template and creates no new revision. Knative refuses a different template under an existing revision name, so a configuration change without a new commit needs another suffix ("${git.short}-${env.BUILD_NUMBER}"), or revisionSuffix: "" to let Knative generate names (then every apply with a change creates a revision, identical applies still do not).

Overrides​

template is deep-merged on the generated Service, for anything the parameters do not cover:

{
  "type": "Webda/KnativeDeployer",
  "image": "ghcr.io/acme/api:${git.version}",
  "template": {
    "spec": { "template": { "spec": { "nodeSelector": { "kubernetes.io/arch": "arm64" } } } }
  }
}

A string is the path of a YAML or JSON file relative to the application, with the same templates. Arrays (containers, traffic, envFrom) replace the generated ones.

Cloud Run​

platform: "cloudrun" produces a manifest gcloud run services replace accepts; applying through the Google API is not supported, run gcloud on the knative manifest output:

webda -d production knative manifest --output service.yaml
gcloud run services replace service.yaml --region europe-west1

Differences with the Knative manifest, logged as warnings when a parameter is dropped:

  • namespace is left out unless set: on Cloud Run it is the project id or number.
  • The autoscaling annotations are autoscaling.knative.dev/minScale and maxScale; target is ignored, Cloud Run scales on containerConcurrency.
  • containerConcurrency is capped to 1000, and 0 is left out (the Cloud Run default is 80); timeoutSeconds is capped to 3600.
  • envFrom is not supported: reference secrets with template (valueFrom.secretKeyRef) or mount them.
  • The readiness probe becomes a startup probe, Cloud Run has no readiness probe.
  • visibility: "cluster-local" becomes the run.googleapis.com/ingress: internal annotation.

Scaling and cold starts​

A scale-from-zero request waits for the pod scheduling, the image pull (cached after the first one) and the application startup. The startup of sample-app (every Webda module, packaged with webda package) was measured at 2.6s median (2.4s to 2.7s over 5 runs, one outlier at 4.9s), from the process spawn to the HTTP port accepting connections, on Node v22.19 and an Apple M-series laptop; unpackaged (webda serve with the module scan) it was 2.8s. Add the pod scheduling (1-3s on an idle node) for the cold start seen by the first request.

  • Keep minScale: 0 for batch-like or internal services where a few seconds of latency do not matter.
  • Set minScale: 1 for latency-sensitive services: it keeps one replica warm at the cost of its resources.
  • maxScale bounds the burst; target (default 100 concurrent requests per replica) decides when a replica is added, containerConcurrency is a hard limit the queue proxy enforces.

Eventing​

Knative Eventing delivers CloudEvents from a Broker to the services a Trigger selects, over HTTP. @webda/cloudevents provides both ends:

  • Webda/CloudEventsReceiver is the sink: a POST route (url, /cloudevents) accepting the binary (ce-* headers), structured (application/cloudevents+json) and batch (application/cloudevents-batch+json) content modes, dispatching every event to the handlers registered on its exact type or a predicate.
  • Webda/KnativeBrokerPubSub is a PubSubService: sendMessage posts a CloudEvent to the Broker ingress, consume registers on the receiver (Knative pushes, nothing polls) and size() is unsupported (0).
  • The deployer triggers parameter generates the Triggers delivering the Broker events to the receiver.
webda.config.jsonc
{
  "services": {
    "CloudEventsReceiver": { "type": "Webda/CloudEventsReceiver", "url": "/cloudevents", "dedupe": true },
    "Events": { "type": "Webda/KnativeBrokerPubSub", "namespace": "apps", "broker": "default" }
  }
}
deployments/production.jsonc
{
  "name": "knative",
  "type": "Webda/KnativeDeployer",
  "namespace": "apps",
  "triggers": [
    { "broker": "default", "filter": { "type": "com.acme.order.created" } },
    { "name": "returns", "broker": "default", "filters": [{ "cesql": "type LIKE 'com.acme.return.%'" }] }
  ]
}

knative manifest prints the Triggers after the Service (one YAML document each), deploy applies them once the Service is Ready (server-side apply, like the Service) and knative delete --yes removes them first. A Trigger subscribes to broker (default) and delivers the events matching filter (exact attributes) or filters (the new-trigger-filters feature: exact, prefix, suffix, all, any, not, cesql) to the Service on path (/cloudevents), so the receiver url and the Trigger path must match. Cloud Run has no Knative Eventing: triggers are dropped with a warning, use Eventarc.

import { CloudEventHandler, CloudEventsReceiver, KnativeBrokerPubSub } from "@webda/cloudevents";
import { Service, useService } from "@webda/core";
import { CloudEvent } from "cloudevents";

class Orders extends Service {
  // Discovered by the receiver when it initializes, like @Route by the Router
  @CloudEventHandler("com.acme.order.created")
  async onCreated(event: CloudEvent<Order>) {
    await Order.ref(event.data.id).patch({ status: "received" });
    // Optional reply, sent back in the response (the Broker delivers it like any event)
    return new CloudEvent({ type: "com.acme.order.received", source: "/orders", data: { id: event.data.id } });
  }
}

// Or at runtime, by type or predicate; the returned function unsubscribes
const receiver = useService<CloudEventsReceiver>("CloudEventsReceiver");
receiver.subscribe(event => event.type.startsWith("com.acme."), async event => { ... });
await useService<KnativeBrokerPubSub>("Events").sendMessage(new CloudEvent({ type: "com.acme.order.created", source: "/orders", data: order }));

Delivery contract​

AnswerWhenKnative
202Every handler succeeded (also: no handler, filtered out, duplicate)Acknowledged
200 with a CloudEventA handler returned a reply (binary mode, a batch in batch mode)Acknowledged, reply delivered
400Not a CloudEvent, or an invalid one (strict adds the SDK schema)Not retried
500A handler threw (a WebdaError.HttpError keeps its own status)Retried, then dead-lettered

A batch is acknowledged as a whole: one failing handler refuses the batch and the sender redelivers it. Delivery is at-least-once: a retry after a lost acknowledgement runs the handler again, so handlers must be idempotent. dedupe: true acknowledges an event already handled with the same source and id without dispatching it (dedupeTtl 1h, dedupeSize 10000 entries); the cache is in memory and per replica, it only catches the retries reaching the same replica and a failed delivery is never remembered. filters (CloudEvents Subscriptions dialects, CESQL included) acknowledges the events not matching without dispatching them: prefer a Trigger filter, which keeps them off the network. Configure the Broker delivery (spec.delivery on the Broker or Trigger: retry, backoffPolicy, deadLetterSink) for the retries, Webda does not retry itself.

A consume callback of Webda/KnativeBrokerPubSub runs in the request of the Trigger with the same contract: its error answers 500 and the Broker retries. sendMessage fails (KNATIVE_BROKER_REJECTED) when the Broker ingress does not answer 2xx, unlike the SDK httpTransport which ignores the status.

Stateless rules​

Knative starts and stops replicas at any time: every replica must be disposable.

  • No in-memory sessions: use a cookie session or a store-backed SessionManager.
  • No in-memory locks or caches holding state between requests: use a store, a queue or a shared cache.
  • No local files beyond the request: use a Binary store.
  • Long-running jobs do not belong in a request: a revision times out at timeoutSeconds.
  • Pull-based queue consumers (webda worker, AsyncJobService with a queue) belong on a Deployment scaled with KEDA, not on a Knative Service: Knative scales on HTTP traffic and stops idle replicas, a consumer polling a queue is never idle from its point of view.
